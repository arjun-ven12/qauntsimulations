# Daytona isolated world execution

Runtime Milestone 4 adds a provider-selectable executor that runs one existing `WorkerJob` in one ephemeral Daytona sandbox. The public Render demo store is not used: its URL works from the developer Mac, but Daytona EU resets the TLS connection during negotiation. The demo store and Playwright worker therefore run together and communicate only over sandbox localhost.

## Architecture

```text
InvestigationOrchestratorService
  -> WorkerExecutor (LOCAL or DAYTONA)
  -> DaytonaPlaywrightWorkerExecutor
  -> DaytonaSandboxProvider
  -> one Daytona EU sandbox
       |- demo store: http://127.0.0.1:4174
       `- Playwright worker
```

`WORKER_EXECUTION_PROVIDER` defaults to `local`. Daytona credentials are parsed only when `daytona` is selected. The orchestrator, persistence layer, evidence API, `WorkerJob`, and `WorkerResult` remain provider-neutral. Daytona mode is deliberately limited to one concurrent sandbox; there is no fleet scheduler in this milestone.

## Configuration

```env
WORKER_EXECUTION_PROVIDER=daytona
DAYTONA_API_KEY=<secret>
DAYTONA_API_URL=https://app.daytona.io/api
DAYTONA_TARGET=eu
DAYTONA_MAX_CONCURRENT_SANDBOXES=1
DAYTONA_SANDBOX_TIMEOUT_SECONDS=300
DAYTONA_AUTO_DELETE=true

DAYTONA_WORKSPACE_PATH=/home/daytona/taskos
DAYTONA_DEMO_STORE_PATH=/home/daytona/taskos/demo-store
DAYTONA_WORKER_PATH=/home/daytona/taskos/worker
DAYTONA_INPUT_PATH=/home/daytona/taskos/input
DAYTONA_EVIDENCE_PATH=/home/daytona/taskos/output
DAYTONA_DEMO_STORE_PORT=4174
```

The prompt's suggested `/workspace/taskos` path is not used. A live sandbox showed that Daytona toolbox commands run as the unprivileged `daytona` user and `/workspace` is neither present nor writable. `/home/daytona/taskos` is the verified writable location. The organization supports the `eu` target but not `us`; there is no automatic region fallback.

The only environment variables sent to the sandbox are `NODE_ENV`, `TASKOS_WORKER_MODE`, `PORT`, `HOST`, localhost demo URLs, and `PLAYWRIGHT_BROWSERS_PATH`. Database, JWT, Daytona, AI-provider, GitHub, and user secrets are never uploaded.

## Portable bundles and layout

The demo upload contains its built `dist/` tree plus a minimal package manifest. It does not contain source, the API, `.env`, or the repository. The worker build uses esbuild to produce a single ESM `worker.mjs` containing TaskOS contracts and Zod, plus a minimal package manifest with the exact Playwright runtime dependency. Browser binaries are installed inside each fresh sandbox.

```text
/home/daytona/taskos/
  demo-store/
    package.json
    dist/
  worker/
    package.json
    worker.mjs
  input/
    worker-job.json
  logs/
  output/
    worker-result.json
    manifest.json
    screenshots/
    trace/trace.zip
    console/console.json
    network/network.json
```

Upload manifests are generated by the API from configured, trusted local paths. Symlinks, secret filenames, path traversal, user-selected executables, shell fragments, and arbitrary upload/download paths are rejected.

## Execution lifecycle

The executor creates an EU sandbox with safe labels and a sanitized name, creates the fixed directories, uploads both bundles and the validated job, installs production dependencies, and installs Chromium. It starts the demo production server in a background Daytona session, then polls `GET /products/test-product` for HTTP 200. It also requires JSON success from `POST /api/test/reset` and `POST /api/test/config` before the worker starts.

The sandbox copy of the job preserves the world, journey, invariants, setup, seed, and limits, but replaces the target URLs with `http://127.0.0.1:4174` and the evidence directory with `/home/daytona/taskos/output`. The canonical database job is not mutated.

The worker runs as a fixed structured command. Exit `0` is a passing execution and exit `2` is a valid invariant-violation result. Worker output and logs are bounded before persistence. Result and manifest JSON are downloaded first and validated with the canonical schemas. Every referenced artifact must resolve beneath the sandbox output root before screenshots, trace, console, and network evidence are downloaded to the existing local evidence directory.

The existing investigation repository persists the validated result, invariant evaluations, evidence metadata, executor provider, real sandbox ID, safe process output, timing metadata, and cleanup outcome. Evidence binaries remain on disk.

## Events, timeouts, cancellation, and cleanup

Provider lifecycle phases are recorded inside the unchanged `InvestigationEvent` data field, including sandbox request/readiness, uploads, setup, demo readiness, worker execution, evidence download, and cleanup.

The overall lifecycle is bounded by `DAYTONA_SANDBOX_TIMEOUT_SECONDS`; creation, commands, process polling, readiness, uploads, and downloads receive the remaining deadline. Readiness failure prevents worker execution and includes bounded process diagnostics.

Cleanup is in `finally`: worker and demo sessions are stopped when possible, then the sandbox is deleted after success, invariant violation, setup failure, timeout, invalid output, download failure, cancellation, or an unexpected error. A deletion failure preserves an already validated result, records `cleanupOutcome=FAILED`, emits `sandbox_cleanup_failed`, and retains the sandbox ID for operator cleanup.

Cancellation is checked before provisioning and before worker start. While a Daytona command is running, cancellation polling can terminate its session; the executor then applies the same cleanup path. Daytona session termination is best-effort, so the sandbox deletion remains the hard isolation boundary.

## Current limitations

- Installing Playwright and Chromium in a fresh default snapshot adds roughly 27 seconds; a controlled prebuilt snapshot could reduce this later.
- The default snapshot currently supplies Node 25 while the repository targets Node 22 or newer. The portable worker is verified on that runtime, but a pinned LTS snapshot is preferable.
- Cancellation and process stopping use Daytona sessions and are best-effort until sandbox deletion completes.
- Only the healthy live scenario is required and verified here; the defective live scenario has not been claimed.
- There is no multi-sandbox fleet, lease/heartbeat scheduler, adaptive follow-up, minimisation, or AI-provider integration.
